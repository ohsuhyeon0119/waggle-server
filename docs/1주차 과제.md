# 과제: 메모리 기반 모임 관리 API 완성하기

세미나에서는 다음 두 API를 구현했습니다.

```
POST /meetings
GET  /meetings/{id}
```

현재 모임을 생성하고 하나의 모임을 조회할 수 있으며,

- 잘못된 생성 요청은 `400 Bad Request`
- 존재하지 않는 모임 조회는 `404 Not Found`

로 처리합니다.

이번 과제에서는 나머지 모임 관리 API를 직접 구현합니다.

```
GET    /meetings
PATCH  /meetings/{id}
DELETE /meetings/{id}
```

완성 코드는 제공하지 않습니다.

각 API의 계약을 확인하고 필요한 Controller, Service, Repository와 DTO를 직접 설계해 봅시다.

---

## 1. 과제 목표와 시작 상태

이번 과제의 목표는 새로운 구조를 배우는 것이 아니라, 세미나에서 경험한 요청 처리 흐름을 새로운 기능에 직접 적용하는 것입니다.

```
API 요구사항 확인
↓
요청·응답 형태 정의
↓
Controller에 API 연결
↓
Service에 기능 구현
↓
Repository에 저장·조회 기능 구현
↓
Validation과 예외 처리 연결
```

과제를 완료하면 다음 다섯 API가 모두 동작해야 합니다.

| 기능 | HTTP Method | URI |
| --- | --- | --- |
| 모임 생성 | `POST` | `/meetings` |
| 모임 목록 조회 | `GET` | `/meetings` |
| 모임 단건 조회 | `GET` | `/meetings/{id}` |
| 모임 수정 | `PATCH` | `/meetings/{id}` |
| 모임 삭제 | `DELETE` | `/meetings/{id}` |

### 과제 시작 시 이미 구현된 기능

#### 모임 생성

```
POST /meetings
Content-Type: application/json

{
  "title": "Spring 스터디",
  "capacity": 10
}
```

```
201 Created
Location: /meetings/1
Content-Type: application/json

{
  "id": 1,
  "title": "Spring 스터디",
  "capacity": 10
}
```

#### 모임 단건 조회

```
GET /meetings/1
```

```
200 OK
Content-Type: application/json

{
  "id": 1,
  "title": "Spring 스터디",
  "capacity": 10
}
```

#### 생성 요청 Validation

다음과 같이 잘못된 요청은 `400 Bad Request`를 반환합니다.

```json
{
  "title": "",
  "capacity": 0
}
```

#### 존재하지 않는 모임 조회

```
GET /meetings/999
```

```
404 Not Found
Content-Type: application/json

{
  "code": "MEETING_NOT_FOUND",
  "message": "ID가 999인 모임을 찾을 수 없습니다.",
  "fieldErrors": []
}
```

과제 기능을 추가한 이후에도 위의 기존 기능이 모두 정상적으로 동작해야 합니다.

## 2. 모임 목록 조회

저장된 모든 모임을 조회하는 API를 구현합니다.

```
GET /meetings
```

### 요청

```
GET /meetings
```

### 성공 응답

저장된 모임을 JSON 배열로 반환합니다.

```
200 OK
Content-Type: application/json

[
  {
    "id": 1,
    "title": "Spring 스터디",
    "capacity": 10
  },
  {
    "id": 2,
    "title": "Kotlin 스터디",
    "capacity": 15
  }
]
```

배열의 각 원소는 기존 단건 조회 API와 같은 응답 형태를 사용합니다.

```json
{
  "id": 1,
  "title": "Spring 스터디",
  "capacity": 10
}
```

### 저장된 모임이 없는 경우

저장된 모임이 없더라도 오류가 아닙니다.

`404 Not Found`가 아니라 `200 OK`와 빈 배열을 반환합니다.

```
200 OK
Content-Type: application/json

[]
```

**빈 목록도 정상적인 조회 결과입니다.**

### 목록 순서

이번 과제에서는 응답 배열의 순서를 API 계약으로 지정하지 않습니다.

생성된 모임이 모두 포함되어 있으면 됩니다.

공개 테스트 역시 목록의 특정 순서에 의존하지 않습니다.

### 생각해 보기

- Repository에서 저장된 모든 모임을 어떻게 가져올 수 있을까요?
- 여러 `Meeting`을 여러 `MeetingResponse`로 어떻게 변환할 수 있을까요?
- 저장된 데이터가 하나도 없다면 Repository와 Service는 무엇을 반환하면 좋을까요?

## 3. 모임 부분 수정

기존 모임의 제목이나 정원을 수정하는 API를 구현합니다.

```
PATCH /meetings/{id}
```

이번 API는 **부분 수정**입니다.

클라이언트는 변경하고 싶은 프로퍼티만 요청 Body에 포함할 수 있습니다.

---

### 제목만 수정

```
PATCH /meetings/1
Content-Type: application/json

{
  "title": "Spring Boot 스터디"
}
```

성공하면 수정된 모임 전체를 반환합니다.

```
200 OK
Content-Type: application/json

{
  "id": 1,
  "title": "Spring Boot 스터디",
  "capacity": 10
}
```

`capacity`를 전달하지 않았으므로 기존 값이 유지되어야 합니다.

```
title
→ 새로운 값으로 변경

capacity
→ 기존 값 유지
```

---

### 정원만 수정

```
PATCH /meetings/1
Content-Type: application/json

{
  "capacity": 20
}
```

```
200 OK
Content-Type: application/json

{
  "id": 1,
  "title": "Spring 스터디",
  "capacity": 20
}
```

이번에는 `title`을 전달하지 않았으므로 기존 제목이 유지되어야 합니다.

```
title
→ 기존 값 유지

capacity
→ 새로운 값으로 변경
```

---

### 제목과 정원을 함께 수정

두 값을 동시에 수정할 수도 있습니다.

```
PATCH /meetings/1
Content-Type: application/json

{
  "title": "Spring Boot 스터디",
  "capacity": 20
}
```

```
200 OK
Content-Type: application/json

{
  "id": 1,
  "title": "Spring Boot 스터디",
  "capacity": 20
}
```

모임을 수정하더라도 `id`는 변경되지 않아야 합니다.

---

### 수정 요청 Validation

수정 요청에서는 `title`과 `capacity` 모두 **선택적으로 전달할 수 있어야 합니다.**

하지만 값이 실제로 전달되었다면 생성 요청과 같은 제약 조건을 만족해야 합니다.

```
title이 전달됨
→ 비어 있거나 공백뿐이면 안 됨

capacity가 전달됨
→ 1 이상이어야 함
```

따라서 다음 요청은 정상입니다.

```json
{
  "title": "Spring Boot 스터디"
}
```

```json
{
  "capacity": 20
}
```

```json
{
  "title": "Spring Boot 스터디",
  "capacity": 20
}
```

반면 다음 값은 허용하지 않습니다.

```json
{
  "title": ""
}
```

```json
{
  "title": "   "
}
```

```json
{
  "capacity": 0
}
```

```json
{
  "capacity": -1
}
```

잘못된 수정 요청에는 기존 생성 API와 동일한 오류 응답 구조를 사용합니다.

```
400 Bad Request
Content-Type: application/json

{
  "code": "INVALID_REQUEST",
  "message": "요청값이 올바르지 않습니다.",
  "fieldErrors": [
    {
      "field": "capacity",
      "message": "모임 정원은 1명 이상이어야 합니다."
    }
  ]
}
```

다음을 만족해야 합니다.

- 상태 코드가 `400 Bad Request`이다.
- 오류 코드가 `INVALID_REQUEST`이다.
- `fieldErrors`에 검증에 실패한 프로퍼티가 포함된다.

여러 필드가 동시에 잘못된 경우 `fieldErrors`의 배열 순서는 평가하지 않습니다.

> 💡 **힌트:** 생성 요청과 달리 수정 요청의 프로퍼티는 생략될 수 있습니다. Nullable 프로퍼티에 사용하는 Bean Validation Annotation이 `null`을 어떻게 처리하는지 확인해 보세요.
> 

필요하다면 세미나에서 사용하지 않은 Validation Annotation을 찾아 사용해도 됩니다.

---

### 존재하지 않는 모임 수정

존재하지 않는 모임을 수정하면 `404 Not Found`를 반환합니다.

```
PATCH /meetings/999
Content-Type: application/json

{
  "capacity": 20
}
```

```
404 Not Found
Content-Type: application/json

{
  "code": "MEETING_NOT_FOUND",
  "message": "ID가 999인 모임을 찾을 수 없습니다.",
  "fieldErrors": []
}
```

기존 단건 조회에서 사용한 `MeetingNotFoundException`과 전역 예외 처리 구조를 새로운 기능에서도 활용할 수 있는지 생각해 봅시다.

---

### Core 과제에서 평가하지 않는 경우

다음 두 요청의 동작은 이번 Core 과제에서 평가하지 않습니다.

#### 수정할 프로퍼티가 하나도 없는 요청

```json
{}
```

#### 명시적으로 `null`을 전달한 요청

```json
{
  "title": null,
  "capacity": null
}
```

위 두 경우에 대한 추가 처리는 자유롭게 구현해도 되지만 Core 요구사항은 아닙니다.

## 4. 모임 삭제

기존 모임을 삭제하는 API를 구현합니다.

```
DELETE /meetings/{id}
```

### 요청

```
DELETE /meetings/1
```

### 성공 응답

삭제에 성공하면 `204 No Content`를 반환합니다.

```
204 No Content
```

`204 No Content` 응답에는 Body가 없어야 합니다.

```
상태 코드
→ 204 No Content

응답 Body
→ 없음
```

---

### 실제로 삭제되어야 한다

HTTP 응답만 `204`로 반환해서는 안 됩니다.

삭제된 모임은 이후 저장소에서도 존재하지 않아야 합니다.

예를 들어 다음 순서로 확인할 수 있습니다.

```
POST /meetings
→ id = 1 생성

DELETE /meetings/1
→ 204 No Content

GET /meetings/1
→ 404 Not Found
```

목록 조회 결과에서도 삭제된 모임은 더 이상 나타나지 않아야 합니다.

```
모임 생성
↓
GET /meetings
→ 목록에 포함됨

모임 삭제
↓
GET /meetings
→ 목록에서 제외됨
```

---

### 존재하지 않는 모임 삭제

존재하지 않는 모임을 삭제하려고 하면 `404 Not Found`를 반환합니다.

```
DELETE /meetings/999
```

```
404 Not Found
Content-Type: application/json

{
  "code": "MEETING_NOT_FOUND",
  "message": "ID가 999인 모임을 찾을 수 없습니다.",
  "fieldErrors": []
}
```

조회와 수정에서 사용한 실패 처리 구조를 삭제에서도 재사용할 수 있는지 생각해 봅시다.

### 생각해 보기

- Repository에서 특정 ID의 모임을 어떻게 제거할 수 있을까요?
- 삭제할 모임이 존재하지 않는 경우 어느 계층에서 이를 판단하는 것이 좋을까요?
- `204 No Content`처럼 Body가 없는 응답은 Controller에서 어떻게 표현할 수 있을까요?

## 5. 공통 API 계약과 오류 처리

과제를 완료하면 다음 API 계약을 만족해야 합니다.

| 기능 | 요청 | 성공 |
| --- | --- | --- |
| 생성 | `POST /meetings` | `201 Created` |
| 목록 조회 | `GET /meetings` | `200 OK` |
| 단건 조회 | `GET /meetings/{id}` | `200 OK` |
| 수정 | `PATCH /meetings/{id}` | `200 OK` |
| 삭제 | `DELETE /meetings/{id}` | `204 No Content` |

오류 상황도 기존 규칙을 일관되게 사용합니다.

### 잘못된 요청값

```
400 Bad Request
code = INVALID_REQUEST
```

예:

- 생성 요청의 빈 제목
- 생성 요청의 `capacity <= 0`
- 수정 요청에서 전달된 빈 제목
- 수정 요청에서 전달된 `capacity <= 0`

### 존재하지 않는 모임

```
404 Not Found
code = MEETING_NOT_FOUND
```

다음 API 모두 같은 원칙을 적용합니다.

```
GET    /meetings/{id}
PATCH  /meetings/{id}
DELETE /meetings/{id}
```

API마다 별도의 오류 구조를 새로 만들 필요는 없습니다.

기존 Validation과 예외 처리 흐름을 재사용해 봅시다.

## 6. 구현 및 평가 기준

### 기존 기능을 깨뜨리지 않기

새로운 기능만 동작한다고 과제가 완료되는 것은 아닙니다.

기존 기능도 계속 정상적으로 동작해야 합니다.

```
POST /meetings
→ 201 Created

GET /meetings/{id}
→ 200 OK

잘못된 생성 요청
→ 400 Bad Request

존재하지 않는 모임 조회
→ 404 Not Found
```

새로운 코드를 추가하면서 기존에 동작하던 기능이 망가지는 현상을 **회귀(Regression)**라고 합니다.

공개 테스트에서는 새로운 기능뿐 아니라 기존 핵심 동작도 함께 확인합니다.

---

### 내부 구현 방식은 자유롭게 선택한다

과제는 기본적으로 **HTTP API 계약을 만족하는지**를 기준으로 확인합니다.

다음 이름을 그대로 사용할 필요는 없습니다.

- 특정 DTO 이름
- 특정 Service 함수 이름
- 특정 Repository 함수 이름
- 특정 변수 이름

다만 세미나에서 배운 구조를 사용할 경우 다음과 같은 흐름을 생각해 볼 수 있습니다.

```
Controller
↓
Service
↓
Repository
```

다른 구조가 더 적절하다고 판단했다면 사용할 수 있습니다.

중요한 것은 선택한 구현이 API 계약을 만족하고, 각 코드가 어떤 책임을 담당하는지 설명할 수 있는 것입니다.

---

### 이번 과제에서 사용하지 않는 것

이번 과제는 **메모리 기반 API의 전체 흐름을 완성하는 것**에 집중합니다.

아직 다음 내용은 사용하지 않습니다.

- 데이터베이스
- JPA
- SQL

데이터는 계속 메모리에 저장합니다.

```
Repository
↓
MutableMap
```

따라서 애플리케이션을 종료하면 저장한 데이터가 사라지는 것은 정상입니다.

현재 메모리 저장소와 ID 생성 방식의 동시성 문제 역시 이번 과제의 평가 범위가 아닙니다.

이 문제들은 이후 주차에서 다시 다룹니다.

## 7. 완료 조건

다음 조건을 모두 만족하는지 확인해 보세요.

### 목록 조회

- `GET /meetings`가 `200 OK`를 반환한다.
- 생성된 모든 모임이 JSON 배열에 포함된다.
- 저장된 모임이 없으면 `[]`를 반환한다.
- 배열의 순서에 의존하지 않는다.

### 부분 수정

- `PATCH /meetings/{id}`가 동작한다.
- 제목만 수정할 수 있다.
- 정원만 수정할 수 있다.
- 제목과 정원을 함께 수정할 수 있다.
- 전달하지 않은 값은 기존 값을 유지한다.
- 수정 후에도 `id`는 유지된다.
- 전달된 제목이 비어 있으면 `400 Bad Request`를 반환한다.
- 전달된 정원이 `0` 이하이면 `400 Bad Request`를 반환한다.
- 존재하지 않는 모임이면 `404 Not Found`를 반환한다.

### 삭제

- `DELETE /meetings/{id}`가 성공하면 `204 No Content`를 반환한다.
- 성공 응답에는 Body가 없다.
- 삭제된 모임은 단건 조회할 수 없다.
- 삭제된 모임은 목록에서도 사라진다.
- 존재하지 않는 모임이면 `404 Not Found`를 반환한다.

### 기존 기능

- 모임 생성 API가 계속 동작한다.
- 모임 단건 조회 API가 계속 동작한다.
- 기존 생성 Validation이 계속 동작한다.
- 기존 `MEETING_NOT_FOUND` 오류 처리가 계속 동작한다.

```
목록 조회
부분 수정
삭제
```

새로운 개념을 많이 추가하기보다, 세미나에서 배운 다음 흐름을 **스스로 다시 구성해 보는 것**이 이번 과제의 핵심입니다.

```
HTTP 요청
↓
Controller
↓
Service
↓
Repository
↓
저장소

그리고

Validation / 예외
↓
일관된 HTTP 오류 응답
```
