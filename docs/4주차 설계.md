# 4주차 설계: 동시성과 트랜잭션

`docs/4주차 과제.md`의 설계 문서 요구에 맞춰, 완성본이 수강 신청·취소와 운영 기능의 정합성을 어떻게 지키는지 적는다.

## 1. 어떤 문제가 있었는가

3주차까지의 수강 신청은 "이미 신청했는가 → 몇 명인가 → 저장" 순서로 확인하고 저장했다. 각 단계는 따로 실행되는 SQL이다.

정원이 1명 남은 세미나에 루키 A와 B가 동시에 신청하면 다음 순서가 가능하다.

```text
A: SELECT COUNT(*) → 29        B: SELECT COUNT(*) → 29
A: INSERT                      B: INSERT
A: COMMIT                      B: COMMIT        → 31명
```

같은 문제가 다른 곳에도 있었다.

| 상황 | 3주차 결과 | 4주차 요구 |
| --- | --- | --- |
| 정원 N에 M명 동시 신청 | N명을 넘겨 저장될 수 있음 | 성공 `min(N, M)`, 나머지 `409` |
| 한 루키가 같은 세미나에 동시 신청 | 두 요청 모두 "신청 안 함"을 보고 저장. 두 번째는 `UNIQUE` 위반으로 `500` | `201` 1건, `409` 나머지 |
| 한 루키가 같은 신청을 동시 취소 | 두 요청 모두 행을 찾고 지움. 둘 다 `204` | `204` 1건, `404` 나머지 |
| 기록이 있는 신청을 취소 | 기록이 수강 신청을 외래 키로 가리켜 `500` | 신청과 기록을 함께 지움 |

## 2. 왜 발생했는가

조회와 저장 사이에 다른 트랜잭션이 끼어들 수 있기 때문이다. `@Transactional`은 여러 SQL을 함께 커밋하거나 되돌릴 뿐, 다른 트랜잭션이 같은 값을 읽는 것을 막지 않는다.

MySQL의 기본 격리 수준(REPEATABLE READ)에서 일반 `SELECT`는 잠금 없이 스냅샷을 읽는다. 그래서 두 트랜잭션이 같은 인원 수를 읽고, 둘 다 "자리가 있다"고 판단한다. 격리 수준을 올리는 것으로는 이 문제가 풀리지 않는다. 확인과 저장 전체를 한 번에 하나씩 실행하게 만들어야 한다.

## 3. 어떤 방법으로 해결했는가

**비관적 잠금**(`SELECT ... FOR UPDATE`)으로 같은 데이터를 다루는 요청을 줄 세운다.

| 작업 | 먼저 잡는 잠금 | 그다음 |
| --- | --- | --- |
| 수강 신청 | 세미나 행 (쓰기) | 중복 확인 → 인원 확인 → 저장 |
| 수강 취소 | 세미나 행 (쓰기) → 수강 신청 행 (쓰기) | 기간 확인 → 기록 삭제 → 신청 삭제 |
| 수강 정보 수정 | 수강 신청 행 (쓰기) | 보낸 항목만 덮어써 저장 |
| 출석·과제 일괄 수정 | 회차 행 (읽기) → 수강 신청 행들 (쓰기, ID 순) | 기록 저장·수정·삭제 |
| 회차 삭제 | 회차 행 (쓰기) | 마지막 회차인지, 기록이 없는지 확인 → 삭제 |

- 한 세미나의 신청과 취소는 세미나 행 잠금을 차례로 얻는다. 잠금을 얻은 요청이 확인부터 저장까지 마치고 커밋해야 다음 요청이 확인을 시작한다.
- 수강 정보 수정, 일괄 기록, 취소는 모두 해당 수강 신청 행을 잠근다. 그래서 취소가 기록을 지우는 사이에 새 기록이 저장되지 않는다.
- 일괄 기록은 회차 행에 읽기 잠금을 건다. 같은 회차를 기록하는 요청끼리는 막지 않지만, 기록하는 동안 회차가 지워지지는 않는다.
- `UNIQUE(seminar_id, rookie_id)`와 `UNIQUE(session_id, enrollment_id)`는 마지막 방어선으로 남겨 두었다. 잠금 덕분에 정상 경로로는 위반되지 않는다. 위반되면 버그로 보고 `409`로 감추지 않는다.

잠그는 메서드는 **READ COMMITTED**로 실행한다(`@Transactional(isolation = Isolation.READ_COMMITTED)`). 이유는 두 가지다.

1. REPEATABLE READ에서는 잠금을 기다린 뒤에도, 일반 `SELECT`가 트랜잭션의 첫 조회 시점 스냅샷을 볼 수 있다. 잠금보다 앞에 조회가 하나라도 있으면 앞 요청이 커밋한 신청을 보지 못한다.
2. REPEATABLE READ는 범위 조건의 `DELETE`와 잠금 조회에 gap lock을 건다. 그래서 서로 다른 수강생을 기록하는 요청끼리도 교착 상태가 생길 수 있다.

순서는 잠금이 정하므로, 각 조회는 그때까지 커밋된 값을 보면 충분하다.

## 4. 왜 그 방법을 선택했는가

| 방법 | 장점 | 이 서비스에서의 단점 |
| --- | --- | --- |
| **비관적 잠금 (선택)** | 확인 로직을 그대로 두고 잠금만 앞에 둔다. 재시도가 없어 결과가 정확하다 | 같은 세미나 요청은 기다린다 |
| 낙관적 잠금 + 재시도 | 충돌이 드물면 기다리지 않는다 | 인기 세미나가 열리는 순간에는 대부분 충돌한다. 명세상 자리가 남았는데 실패하면 안 되므로 재시도 횟수와 간격을 정해야 한다 |
| 조건부 갱신 (`UPDATE ... SET enrolled_count = enrolled_count + 1 WHERE enrolled_count < capacity`) | 잠금 범위가 가장 짧다 | 인원 칼럼을 새로 두고, 취소·탈퇴·롤백마다 실제 신청 수와 맞춰야 한다 |

신청과 취소는 짧은 트랜잭션이다. 잠금으로 기다리는 범위도 같은 세미나로 한정된다. 그래서 정확성과 단순함을 우선해 비관적 잠금을 골랐다.

수강 정보 수정의 `version`(낙관적 잠금)은 4주차 명세에 따라 없앴다. 대신 수정할 때 행을 잠그고 최신 값에 보낸 항목만 덮어쓴다. 그래서 한 운영진은 Grace Day를, 다른 운영진은 탈락 여부를 동시에 고쳐도 두 변경이 모두 남는다. 같은 항목을 고치면 나중 요청이 남는다.

## 5. 트랜잭션 경계는 어디인가

아래 각 묶음은 한 트랜잭션이다. 어느 단계에서 실패해도 앞선 변경까지 모두 되돌린다. 업무 예외(`ApiException`)와 DB 예외는 모두 `RuntimeException`이라 Spring의 기본 규칙대로 롤백된다.

- **출석·과제 일괄 수정** (`DashboardService.updateRecords`)
  - 회차와 수강 신청 잠금
  - 요청한 모든 수강생의 출석 기록 저장·수정·삭제
  - 과제 기록 저장·수정·삭제
- **수강 취소** (`EnrollmentService.cancelMine`)
  - 세미나와 수강 신청 잠금
  - 그 신청의 출석 기록 삭제
  - 과제 기록 삭제
  - 수강 신청 삭제
- **회원 탈퇴** (`UserService.withdraw`, 5주차 범위)
  - 신청 기간이 남은 세미나마다 위의 취소와 같은 삭제
  - 사용자 상태 변경

잠금 순서는 언제나 **세미나 → 수강 신청(ID 순) → 기록**이다. 사용자 행은 마지막이다. 회차는 기록보다 먼저 잠근다. 모든 경로가 같은 순서로 잠그므로 서로가 잡은 잠금을 기다리며 멈추지 않는다.

## 6. 어떻게 검증했는가

```bash
./gradlew test
```

**운영진 공개 테스트** (`src/test/.../auth`, `enrollment`, `seminar`, `session`, `user`)

- `EnrollmentConcurrencyApiTest`: 정원 경쟁(정원 30에 100명 등), 마지막 빈자리 경쟁, 같은 루키의 동시 신청 20회, 동시 취소 10회, 신청·취소 혼합
- `EnrollmentRecordsLifecycleApiTest`: 취소하면 기록이 정리되고, 다시 신청하면 초기 상태로 시작
- `SessionRecordsApiTest`, `EnrollmentManagementApiTest`, `SeminarDashboardApiTest`, `Operations*ApiTest`: 새 엔드포인트의 계약과 전체 반영 여부

**완성본 자체 테스트** (`src/test/.../waggle`)

`RecordsRollbackTest`는 실제 MySQL에 쓴 뒤의 롤백을 확인한다. 순서는 다음과 같다.

1. 바꿀 값과 다른 기록을 API로 저장하고 커밋한다.
2. 테스트 설정에서 과제 기록 저장소를 감싼 빈(`FailingSubmissionRepository`)을 `@Primary`로 등록한다. 이 빈은 지정한 다음 한 번의 `save`에서만 예외를 던진다. 운영 코드는 바꾸지 않는다.
3. 실제 `DashboardService.updateRecords`를 부른다. 이때 처리 순서는 첫 수강생의 출석 수정, 과제 삭제, 둘째 수강생의 출석 수정, 그리고 과제 저장이다. 마지막 과제 저장에서 실패한다.
4. 실패하기 직전 같은 트랜잭션 안에서 기록을 읽어 둔다. 앞선 세 번의 쓰기가 실제로 DB에 반영되어 있었다는 증거다.
5. 예외가 호출자에게 전달되었는지 확인한다.
6. 새 트랜잭션에서 다시 읽어, 모든 기록이 작업 전과 같은지 확인한다.

Migration은 두 경우를 모두 확인했다.

- **빈 DB**: Testcontainers가 V1~V4를 차례로 적용한다.
- **기존 DB**: 새 MySQL에 V1~V3까지만 적용해 시연 데이터(수강 신청 7, 출석 11, 과제 10)를 만들었다. 그 뒤 새 코드로 기동해 V4를 적용했다. 행 수는 그대로였고, `enrollments`에서 `version` 칼럼만 빠졌다.

## Migration

`V4__drop_enrollment_version.sql`이 `enrollments.version` 칼럼을 지운다. 낙관적 잠금에 쓰던 칼럼으로, 이제 읽지도 쓰지도 않는다. 다른 테이블과 기존 사용자·세미나·수강 신청·기록 데이터는 그대로다. 출석·과제 기록 테이블과 두 `UNIQUE` 제약조건은 V1부터 있었으므로 새로 만들지 않았다.
